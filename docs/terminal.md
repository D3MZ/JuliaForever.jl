# Terminal

The `jf` command accepts a prompt in its arguments. With no prompt it reads one message per input line and `/exit` ends the session. A terminal input displays a banner and prompt on stderr; piped input does not. The same agent and its conversation are retained for the lines in one process.

The CLI saves a new SQLite session automatically when its first turn starts. Use `jf --continue` (or `-c`) to open the most recently modified session for the current working directory; if none exists, it starts a new session. Use `jf --resume` (or `-r`) to choose a project session from a numbered list, or `jf --session PATH|ID` to open an existing session by path or unique ID fragment. During a conversation, `/resume` opens the same selector and switches to the chosen session. Enter `q` or an empty line to cancel the selector. `jf --no-session` keeps the initial conversation in memory; if you use `/resume`, subsequent messages are saved in the chosen session. The selector is line-oriented and does not yet support Pi's search, rename, delete, sorting controls, or cross-project browsing.

If `/resume` rejects a selection or encounters an expected filesystem error while opening it, the current session remains active. Other exceptions propagate. Picker titles and IDs, session paths and filesystem diagnostics redact the configured provider key in raw text and standard single-layer Julia `repr` strings. Other encodings and repeated escaping are not decoded.

Sessions are stored under `~/.julia/juliaforever/sessions` by default. Set `JF_SESSION_DIR` or pass `--session-dir DIR` to use another directory; the flag takes precedence. Sessions for different working directories remain separate even in a shared directory. The CLI creates a session file only when a turn starts, with owner-only file permissions. Paths and IDs refer to Julia Forever's SQLite histories, not Pi's JSONL files.

Enter `/tree` between turns to list the session's user messages and completed assistant responses, including other branches. Selecting a user message offers it for editing; submitting it starts a new branch. An empty edit keeps the original text, and `/cancel` aborts. Selecting an assistant response moves to that point and waits for the next message. `q` cancels the selector. Other branches remain in the history. A selection takes effect in the current process; reopening selects the last appended branch, as in Pi. The selector is line-oriented and does not yet support Pi's full tree UI, branch summaries, or selecting intermediate tool entries. Naming and forking are also not implemented.

`jf --history session.sqlite 'first prompt'`, followed by `jf --history session.sqlite 'next prompt'`, continues to record and resume an explicitly chosen file. The file holds one history; a standalone history is not added to automatic session discovery. SQLite.jl is installed with JuliaForever. Initial project instructions are retained in the history; resuming uses the current provider, tool configuration, and working directory. Session files can contain conversation text, instructions, tool calls and results, so protect them as you would the conversation. Place options before the prompt.

If a prior turn has a pending effect or is incomplete, the CLI exits with a diagnostic and the history file path before requesting the provider or running a tool. It never automatically retries the effect. Run `jf --history PATH --inspect-history` to display the recorded pending effects and tool arguments, and inspect external state before deciding what happened. Then record an explicit decision with `jf --history PATH --abandon 'inspected external state'`. Neither command requires provider configuration or dispatches a request or tool. Abandoning records the reason but does not undo an effect. Reopen the session to start a new turn.

The inspection output can contain sensitive tool arguments. Abandonments recorded by older versions as `Interrupt` events can lack matching tool replies, which strict providers may reject. See [history storage](history.md) for database and platform limitations. Concurrent changes may cause a revision rejection; reopen and inspect before proceeding.

Assistant text is written and flushed as it arrives on stdout, with a newline after each assistant message when needed. Tool starts and outcomes go to stderr; successful tool output and tool arguments are not displayed. Tool errors are displayed with the configured provider key redacted. Incomplete responses are reported without the provider's raw error payload. Raw provider events and HTTP response bodies are not intentionally logged; recognized HTTP and malformed JSON failures omit their details. Assistant text is output as received and is not filtered. The `--login-openrouter` flow writes its authorization URL and code prompt to stdout; `--login-openrouter-callback` writes an authorization URL and waits for a local browser callback.

The command returns 0 after a completed response, including one that recovered from a tool error; 1 for an incomplete response or failed request; 2 for invalid provider configuration or a login response without a key; and 130 for a cancelled request. In a line-oriented session the highest status from its turns is returned. HTTP failures are reported by status or exception type, and malformed JSON is reported without its contents. Other exceptions propagate from the Julia task.

This is a line-oriented interface, not Pi's full-screen editor. It has no multiline editing, slash commands beyond `/exit`, `/tree`, and `/resume`, streaming tool output, live steering, or terminal controls for cancellation. The agent loop and stream callbacks run in one Julia task, and the terminal waits for each request to finish. Synthetic mock and loopback tests cover the documented behavior. With `PI_SOURCE` configured, session discovery, recent selection, branch contexts, and retained user and assistant text are compared with the pinned Pi session manager; this does not test Pi's terminal UI. A real-provider interactive terminal session has not been verified.
