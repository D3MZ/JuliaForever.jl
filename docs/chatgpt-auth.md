# ChatGPT plan sign-in design

ChatGPT plan sign-in is not implemented. Internal callback, code exchange and ID-token verification components are covered by synthetic fixtures, but they are not connected to login or inference. [OpenAI documents a public-client flow](https://developers.openai.com/siwc/token-sharing-open-source) for open-source and locally hosted apps. Eligibility for this project has not been established; paid or remotely hosted apps have a separate interest process. An authorized plan access token is not an API key, and a subscription alone does not grant this project a credential.

The following work remains before accepting a login:

- The internal callback starts a loopback listener with fresh state, nonce and PKCE, validates the issued or saved client ID, and keeps the exact redirect URI. It requires a supplied host ID. The exchange keeps verified credentials in memory. Persist the host ID and sessions, and test service compatibility. See [registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).
- The internal verifier checks RS256 signatures with the fixed OpenAI JWKS, issuer, issued-client audience, expiry, nonce, subject, returning identity and direct-use scope. Its keys and token cases are synthetic; no OpenAI-issued token has been tested. Integrate it with the authorization transaction, use OpenID discovery as needed, and verify service compatibility. OpenAI's [website guide](https://developers.openai.com/siwc/website) describes discovery and ID-token validation.
- Keep each validated account registration and its tokens in protected storage, separate from other accounts. Refresh near expiry with the issued client ID and serialize refreshes for each session; retain replacement tokens. Implement sign-out and revocation according to [accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions).
- Add a distinct plan provider rather than treating a plan token as a generic API key. It must always stream Responses requests with `store=false`, replay required input history, handle terminal stream errors and apply the [preview field and tool restrictions](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations). The current Responses adapter permits nonstreaming, caller-supplied unsupported fields and system messages, and emits flat function tools; those behaviors are not sufficient for the plan route. Plan use also requires an eligible account and explicit consent; missing scope must not proceed to inference.
- Test discovery, callback, token exchange, key rotation, signed and invalid ID tokens, refresh races, credential isolation, request restrictions and streaming failures with synthetic local fixtures. Test a real login and an eligible model request separately only when authorized; fixture tests alone do not establish service compatibility.
