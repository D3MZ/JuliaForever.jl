# Model catalog

`jf --list-models [search]` lists chat models for providers with available credentials, showing context and output limits, reasoning, and image-input metadata. Search accepts space- or slash-separated fuzzy terms. Listing does not contact a provider.

`--model` resolves a case-insensitive model ID, provider-prefixed ID, or ID/name substring. When several providers offer the same ID, configured credentials can select a single provider; otherwise use `--provider` or a `provider/model` reference. Exact catalog IDs containing slashes or colons remain valid. Unknown IDs continue to work with the selected or default provider, except that recognized thinking suffixes are rejected as described below. Recognized OpenAI catalog models use the Responses adapter; explicitly selecting `openai-responses` has the same effect. Environment model variables still select literal IDs using their configured adapter.

The bundled snapshot contains 457 chat models: OpenAI Responses, Anthropic Messages, Google Generative AI, and OpenRouter Chat Completions. It was generated on 2026-10-30 using Pi revision `e7a0df27c09d11bf4161d3605246cbf57a129cb2` and that generator's live upstream sources. The snapshot can become stale and does not guarantee current availability, limits, or pricing. OpenRouter models whose Pi catalog entry uses its Anthropic API are omitted; this harness does not yet implement that transport. Image and reasoning columns describe the catalog, not a promise that every request path supports all capabilities.

The CLI reads `models.json` from `PI_CODING_AGENT_DIR` (default `~/.pi/agent`). Its `providers` entries can add models or override built-in providers and models. Supported APIs are `openai-completions`, `openai-responses`, `anthropic-messages`, and `google-generative-ai`. Provider `baseUrl`, `apiKey`, `headers`, and `authHeader`, model `baseUrl` and `headers`, and the catalog fields `id`, `name`, `api`, `reasoning`, `input`, `contextWindow`, and `maxTokens` are applied. Model definitions replace matching built-in models; `modelOverrides` updates matching model metadata and headers. A model's URL takes precedence over its provider URL. Selecting another configured model reloads its URL and headers from the startup configuration; switching between API types is unavailable. If a custom provider is named `openai-responses`, that name selects the custom provider; use `openai` to select built-in OpenAI models.

For example, with `LOCAL_API_KEY` set, this adds a model selected by `jf --model local/example`:

```json
{
  "providers": {
    "local": {
      "baseUrl": "http://127.0.0.1:8080/v1",
      "api": "openai-completions",
      "apiKey": "$LOCAL_API_KEY",
      "models": [{ "id": "example" }]
    }
  }
}
```

Keys and headers support literals and `$NAME` or `${NAME}` environment references. A stored `auth.json` API key for the provider takes precedence; a saved OpenRouter login takes precedence over its Pi credential. Unsupported stored credential types do not fall back to the configured key. Missing references and unsupported APIs fail before a request. Secret-bearing configuration is redacted from model-registry displays and malformed JSON diagnostics. The file accepts Pi-style `//` comments, trailing commas, and a leading UTF-8 BOM. Custom OpenAI and Anthropic providers can use authentication headers instead of a key; see [providers](providers.md). Julia Forever uses integer token limits and does not execute `!command` values. Pi also supports fractional token limits, credential commands, and OAuth. Configured compatibility, sampling, thinking maps, prompt cache, input limits, and OAuth fields are rejected for requests; pricing metadata is not used. The configuration is read at startup, not refreshed while a session runs. OpenRouter's interactive login currently bypasses these request overrides.

For an unknown model ID on a configured built-in provider, Julia Forever uses the provider's configured API when present and rejects unsupported APIs. Without one, OpenAI falls back to Chat Completions. The pinned Pi revision instead inherits the API of a built-in fallback model, which is Responses for OpenAI.

The library exposes `JuliaForever.Models.catalog()`, `JuliaForever.Models.catalog(path)`, and `JuliaForever.Models.resolve(text, models, usable; provider=nothing)`. A malformed configuration yields `Models.InvalidConfig`; the CLI reports an error without including its contents. Resolution returns typed `Resolved`, `Ambiguous`, or `Unmatched` values and identifies Pi thinking suffixes. The CLI supports thinking suffixes for catalogued OpenAI Responses models at levels explicitly mapped in the pinned Pi catalog. For Google, `gemini-3-flash-preview` supports `off`, `minimal`, `low`, `medium`, and `high`; `gemini-3.1-pro-preview` supports `off`, `low`, `medium`, and `high`. As in Pi, Google `off` selects `minimal` for Flash and `low` for Pro and still requests thoughts. Other Google models, unsupported levels, unknown models, and configured provider overrides reject suffixes before a request; Pi supports additional models and may clamp unsupported levels. Without a suffix, ordinary Google CLI requests do not specify a thinking level; RPC uses `medium` for these two models. Other Google models and configured Google providers expose only `off` in RPC and do not set a Google thinking configuration; Pi can control thinking on configured reasoning models.

Anthropic Messages also supports `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, and `max` for the catalogued Haiku 4.5, Opus 4.5, and Sonnet 4.5 IDs (including dated aliases); `xhigh` and `max` use the high budget. Adaptive and mid-conversation Anthropic effort models, OAuth credentials, configured providers, and interactive Anthropic suffix changes remain unsupported. A supported active budget is retained when switching to another supported Anthropic model; incompatible switches are rejected. Context-window clamping uses reported usage when a native response matches the retained transcript prefix, and estimates otherwise. If tools change, it conservatively adds the current tool declarations. Near the context limit, results can differ from Pi when a matching native usage measurement is unavailable.

GPT-6 models that use `configuration_update` preserve each reply's effort in recorded sessions, keeping the request's top-level effort stable across non-off changes. As in Pi, `off` uses a separate top-level effort and omits updates. Interactive `/model` accepts thinking suffixes for these GPT-6 models; other interactive suffixes remain unsupported. For OpenAI Responses, reselecting a model preserves a supported active effort, and incompatible model switches are rejected instead of clamped. A bare `/model` switch between the two supported Google models retains the active level or raises it to the next available level. Non-off GPT-6 updates require the API-key route and reject a ChatGPT-style token or overridden authorization at the official OpenAI endpoint. The full-screen picker lists models for the current provider. Online refresh, the complete provider catalog, model cycling, picker provider switching, and scoped-model settings remain unsupported.

To refresh the snapshot, run the pinned Pi checkout's `packages/ai/catalog/generate.ts --strict --json-only --json-output CATALOG_DIRECTORY`, then run `julia --project=. scripts/model_catalog.jl CATALOG_DIRECTORY data/models.json`. The Pi generator fetches external catalogs, so regeneration on a different date may produce different values. Review the generated diff and repeat the differential tests before committing it.

To refresh the OpenAI thinking mappings from the matching pinned `@earendil-works/pi-ai` package, run `julia --project=. scripts/openai_thinking.jl PATH_TO_DIST/providers/data/openai.json data/openai-thinking.json` and review them alongside the catalog.
